# ADR 0007 — The Assistant on the web: a gateway app built from this repository, one component library for every host, separate layouts

Status: Proposed
Date: 2026-10-26
Relates to: [ADR 0001](0001_gateway_native_assistant_v2.md) (gateway as authority, one managed
workflow), backlog [1057](../backlog/planned/1057_web_assistant.md), backlog
[0003](../backlog/proposed/0003_tauri_shell_spike.md) (Tauri shell spike), [ADR 0008](0008_desktop_host.md)
(the desktop host stays PyQt5 for this cycle; a Rust/Tauri shell is a spike gated on a change of
goal). This ADR only fixes what any host of these components must provide.
Amended 2026-10-26 after the adversarial review (`untracked/apple-web-wave/adversary.md`): layouts,
follower, wait guard, tool lists, voice per platform, CI.

## Context

The operator wants a web version of AbstractAssistant. `abstractcode/web` already runs in a browser
against the gateway, but it is built for coding (workflow pickers, workspace panes, traces) and is
intimidating for a non-technical person. The Assistant is meant to be the framework's most
approachable surface: a conversation, an orb for voice, approvals and questions inside the
conversation, the same durable conversations on every device. The iPhone app is the nearest model:
a thin gateway client with three spaces (Assistant, Inbox, Automations) whose only state of record
is the gateway's (`phone/iphone/docs/architecture.md:33-41`).

What already exists and is verified (citations are to the live checkouts, 2026-10-26):

- **Browser apps are gateway apps.** The gateway installs `@abstractframework/<name>` from npm,
  starts it on `127.0.0.1` and serves it at `/apps/<id>/` on its own address, signed in per app
  (`abstractgateway/docs/apps.md:143-194`). It serves ONLY apps in its catalog
  (`abstractgateway/src/abstractgateway/apps_manager.py:132-158`, `APPS`; `app_proxy.py:388`
  `APP_BY_ID`) that announce `X-AbstractFramework-App: <id>; mount=1` (`apps.md:182-190`). The
  catalog id `assistant` is taken by the desktop app's row (`apps.md:506-595`).
- **The browser never holds a gateway token.** The app's own server (abstractuic
  `@abstractframework/app-server`) trades a user token for a gateway browser session and keeps it
  in HttpOnly app cookies (`abstractuic/app-server/README.md:182-208`); the gateway's one-time
  handover sets those cookies when the console opens the app (`apps.md:268-289`); the gateway's
  proxy relays only the app's own `<prefix>_*` cookies and never an `Authorization` header
  (`app_proxy.py:82-100,154`). Gateway sessions: `security.md:91-119`
  (`/session/login`, HttpOnly session + readable CSRF cookie, `X-AbstractGateway-Session` /
  `X-AbstractGateway-CSRF`). `/session/claim` is the first-run admin link and answers loopback
  peers only (`routes/gateway.py:468-530`): not a path for this app.
- **Relative URLs.** Apps fetch `api/gateway/…` relative to `<base href>` (kit `gatewayApiPath`,
  `abstractuic/ui-kit/src/gateway_paths.ts:1-26`); abstractcode enforces it with
  `web/scripts/check_relative_urls.mjs`.
- **The run contract is the desktop's.** The next turn starts `@default` + interface
  `abstractassistant.agent.v1` when the gateway reports a default for it, else the managed
  `abstractassistant-orchestrator`, else an account-chosen workflow; never another one silently
  (`abstractassistant/controller.py:579-615`, `gateway_service.py:201-235,570-609`,
  `preferences.py:183-198`). The local gateway reports
  `abstractassistant-orchestrator@0.0.16:c53b1579` as that default (W3 report, proven).
  Input data: `abstractassistant/gateway/run_input.py:83-264`; start: `ui/gateway_worker.py:1180-1206`.
- **Live and durable events.** Per-run ledger SSE with resumable cursors and live reply deltas
  (`abstractgateway/docs/api.md:502-588`), durable commands for resume/cancel (`api.md:988-1024`,
  `client.py:209-245`), the person's own event stream (`api.md:1286-1366`), the history bundle
  (`api.md:1733-1772`), voice routes (`api.md:1805-1844`), attachments upload (`api.md:850-866,966-975`).

## Decision

### 1. Location: `web/` at this repository's root

The web Assistant lives in `abstractassistant/web/`, beside `phone/` and `watch/`, as
abstractcode keeps `web/` beside its TUI. It is the same product as the desktop and Apple apps and
shares their contract tests (the session fold runs on `tests/basic/fixtures/gateway_runs/`, the run
input on cases generated by `gateway/run_input.py`), so it belongs with them, not in the Python
package. The wheel ships only `abstractassistant*` packages (`pyproject.toml`
`[tool.setuptools.packages.find]`) and the sdist only what `MANIFEST.in` names: a build of both
from a copy of this tree with `web/node_modules` present contains no `web/` entry (W3 report,
proven). `.gitignore` excludes `web/node_modules/` and `web/dist/`. Recommended belt (owner:
assistant, the Python packaging): add `prune web` to `MANIFEST.in`, as `prune watch` is there, so a
future setuptools-scm cannot pull tracked `web/` files into the sdist.

### 2. Stack: Vite + React 18 + TypeScript, the kit where it fits

Same stack and pins as abstractcode/web (Vite 6.4.3, React 18.3.1, TypeScript 5.9.3, Vitest 5.0.4;
exact versions, Node 18+, developed on 24). From abstractuic, pinned exactly:

| Use | Package | Why |
|---|---|---|
| App server: mount, flags, gateway pointer, session proxy | `@abstractframework/app-server` 0.1.12 | The only supported way to be served at `/apps/<id>/` without holding tokens |
| Sign-in modal + connection state machine | `@abstractframework/ui-kit` 0.8.7 (`useGatewayConnection`, `GatewayConnectModal`) | "Do not hand-roll it" (`abstractuic/docs/adoption-guide.md`, Gateway connection surface) |
| Relative API paths, relative time | ui-kit `gatewayApiPath`, `joinBaseUrl`, `formatRelativeTime` | Shared rules |
| Markdown answers | `@abstractframework/panel-chat` 0.4.1 `Markdown` with `images="link"` | A model's text cannot make the browser fetch a remote image |
| v2 Automations space | ui-kit `AutomationPanel` + typed automations client (`ui-kit/src/automations/`) | Exists; transport injected |

Built here: the conversation layout, composer, approval and question cards, the turn reducer and
follower, the voice glue, and the orb (W4's design, `web/design/`). The Assistant's look is its own:
the app imports the kit's `theme.css` only for kit components and aliases the kit's token names to
the Assistant's `--aa-*` tokens (`web/design/tokens.css`, W4) after it.

Evaluated and NOT adopted for v1: panel-chat `WorkflowSessionController` / `useWorkflowSession`
(a full run-session machine with injected transport, `panel-chat/src/workflow_runtime.ts`). It
handles subworkflow delegation and approvals, but the Assistant's wait identity rule
(run, wait key, step id — the desktop's 2026-07-28 and 2026-09-07 stalls) is pinned by this
repository's fixtures, and the turn reducer here is ~300 lines with those fixtures as tests.
Phase 1 re-evaluates: if the controller passes `src/lib/run_events.test.ts`'s cases, the web app
adopts it and deletes its reducer (owner: uic + assistant).

### 3. Served as a gateway app

- npm package `@abstractframework/assistant` (name free on npm, 2026-10-26), `bin`
  `abstractassistant-web`; `private` until the gateway lists it.
- Proposed catalog id **`assistant-web`**, display name "Assistant (web)", cookie prefix
  `abstractassistant`, page title starting `AbstractAssistant`, usual port **3008** (3001-3006 are
  the stack map, 3000/3007 legacy probe ports, `apps_manager.py:115-128`). The id cannot be
  `assistant` (the desktop row). Gateway ask G1: an `AppSpec` entry, the stack port, the flag set
  (`FLAG_CONFIGURED_APPS`, `apps_manager.py:165`), and how the console presents two "Assistant"
  rows (desktop and web).
- `web/bin/server.js` is abstractcode's server reduced to this app: `createMountedHandler`
  (identity header, base path, real client address), `injectShell` (`<base href>` +
  `window.__ABSTRACT_UI_CONFIG__ = {host: "browser", base_path}`), the kit's session proxy for
  `api/connection/gateway` and `api/gateway/*`, and abstractcode's three guards in front of it
  (same-origin mutations, JSON sign-in, DNS-rebinding guard). Ask U1 (uic): absorb those guards
  into app-server so the apps stop copying them.
- All browser URLs are relative; `web/scripts/check_relative_urls.mjs` (abstractcode's, ported)
  fails the build on a root-absolute `/api`, `/assets` or `/apps` literal in `src/`, `index.html`
  or `dist/`.

### 4. Hosts: one component library, separate layouts

A browser page and a palette docked under a menu-bar icon (about 420x700, tall) are different
shapes (operator, 2026-10-26), so this is NOT one UI for every host. What is shared is the
component library: the orb, the conversation cards (messages, approvals, questions), the composer,
the inbox rows, the design tokens (`web/design/tokens.css`), and everything under `src/lib/` and
`src/gateway/`. Each host gets its own layout:

| Layout | Width | Shape |
|---|---|---|
| Wide browser | ≥ 1024 px | sidebar (conversations) beside the conversation (`web/design/README.md`, Layouts) |
| Narrow browser | 600-1023 px | one column; the conversation list is a sheet behind the header's Conversations button |
| Phone browser | < 600 px | the same column with tighter gutters; the tab bar of the design is v1.1 |
| Compact palette (a desktop host) | ~420 px wide, tall | a third layout, not the browser page: the palette's own arrangement of the same components (ADR 0008 decides whether and when a non-Qt host exists) |

The browser layouts are checked in headless Chromium at 420, 760, 1024 and 1280 px with a long
title (`web/scripts/check_layout.mjs`, in CI): no sideways scroll, no control off screen, every
button and link at least 44 px.

Everything host-specific goes through ONE interface, `web/src/host/types.ts`:

| The frontend needs | Browser host (implemented) | A desktop host must provide |
|---|---|---|
| `gatewayUrl(route)` | relative `api/gateway/<route>` under `<base href>` | an absolute `http(s)://<gateway>/api/gateway/<route>` |
| `auth.headers(mutating)`, `auth.credentials` | app-cookie session: `credentials: "same-origin"`, `X-AbstractAssistant-CSRF` from the readable CSRF cookie on mutations; throws when the cookie is gone | a bearer token or gateway session held by the native side, injected per request (or a native fetch proxy); never in the page's storage |
| `signIn` | `app-server-modal` (kit modal → `api/connection/gateway`) | `host-native` (the shell signs in, e.g. through the gateway's desktop handover, `apps.md:555-565`) |
| `capabilities` | tray, global hotkey, autostart: unavailable with the sentence why; notifications: unavailable in v1; microphone: available only in a secure context with getUserMedia + MediaRecorder; playback: Web Audio | each one implemented or reported unavailable the same way |

Consequences already in the scaffold: no module outside `src/host/` builds a URL or reads a cookie;
SSE is read with `fetch` + a stream reader (`src/gateway/sse.ts`), not `EventSource`, because
`EventSource` cannot send an `Authorization` header; `resolveHost` throws for `host: "tauri"`
("not implemented") rather than guessing.

Voice per platform (sourced, not run here: `untracked/apple-web-wave/adversary.md` §3(a), from
wry 0.57.1 / Tauri 2.12.5, MDN, the WebKit blog and Ubuntu's package versions):

| | Browser (this ADR) | macOS WKWebView | Windows WebView2 | Linux WebKitGTK |
|---|---|---|---|---|
| Capture (`getUserMedia`) | secure pages only | works; needs `NSMicrophoneUsageDescription` and the `device.audio-input` entitlement; a double prompt is open (wry#1195) | prompts and names `http://tauri.localhost`; a saved "Block" sticks; Tauri ≥ 2.12 `on_permission_request` | denied by default: wry never enables media streams; needs `set_enable_media_stream`, a permission handler and GStreamer's pipewire/pulse plugins |
| Encoding (`MediaRecorder`, what dictation uses) | Chromium/Firefox webm, Safari mp4 | `audio/mp4` only before Safari 18.4 | webm | **broken on stock Ubuntu**: WebM needs GStreamer ≥ 1.24.9 (22.04 ships 1.20.3, 24.04 ships 1.24.2) |
| Playback (`decodeAudioData` + scheduled buffers, read aloud) | works | works | works | works |
| Output device name, system volume, choosing the device | no | no (no `setSinkId` on WebKit) | partial | no |

Decisions:

- **Dictation with `MediaRecorder` is a browser-host feature.** It stays as built for the browser
  (`src/lib/voice.ts`).
- **A desktop host captures raw PCM with an AudioWorklet** (Chrome 66+, Safari 14.1+, WebKitGTK
  WebAudio on by default), encodes WAV in the page, and uploads it on the same path
  (`attachments/upload` then `audio/transcribe`, which accepts `audio/wav`). Voice activity
  detection then runs in WASM in the page (Silero through onnxruntime-web, or webrtcvad compiled
  to WASM) or in the host. Not built: it belongs to the host that needs it (ADR 0008's gate).
- Read aloud stays in the frontend for every host.
- A host keeps a small native shim for what no WebView can do: device names, system volume,
  choosing the output.

What any non-browser host must also add: the WebView's media permission handler, a CSP and a
gateway CORS rule for its origin (`tauri://localhost` on macOS and Linux, `http://tauri.localhost`
on Windows), the bearer-header auth adapter (the browser's cookie session does not carry over),
the token store, tray and badge, global hotkey, notifications, autostart, and opening artifacts
with the system.

### 5. Auth in the browser

Follow `security.md:91-119` through the app server; nothing else. The person signs in once in the
kit's modal (user id + token, sent to this app's server, never stored by the page), or arrives
already signed in through the console's **Open** (one-time handover, app cookies at
`Path=/apps/assistant-web/`). The page stores no token, no session id and no conversation in
`localStorage`, `sessionStorage` or IndexedDB. A 401 sends the person back to the modal. With user
accounts off only admins can hold a browser session (`security.md:112-133`): the modal shows the
gateway's sentence.

### 6. The run contract: the same managed workflow, presence check only

- **Which workflow:** `GET /bundles?executable_for=abstractassistant.agent.v1` and
  `GET /accounts/me/preferences` before every send, then the desktop's rule
  (`src/lib/workflow_selection.ts`, a port with the same refusals). The web client **never
  publishes, promotes or edits a workflow** (backlog overview item 0): when none is runnable it
  shows the gateway's reason and sends nothing.
- **Input:** `src/lib/run_input.ts`, a port of `build_run_input_data` with the same argument
  names; parity is a test over cases generated by the Python builder. v1 sends
  `use_session_history: true` (the gateway replays history), the uploaded `$artifact` refs (and the
  first image as `primary_image_artifact`), and `_runtime.stream: true` (live answers are the
  point of a web UI). Not ported: per-route media overrides and speculation.
- **Tools (decided after review, adversary finding 7):** every send carries explicit
  `allowed_tools` and `tool_policy`, the desktop's lists for the same gateway answer with no local
  per-tool settings (`src/lib/tool_policy.ts`, a port of `controller.py:1664-1842`; parity cases
  generated by the desktop's controller, `web/scripts/gen_tool_policy_parity.py`): every tool the
  gateway enables (`GET /discovery/tools`, `enabled` not false), auto-approved only when the gateway
  says `approval_default: "auto"`, every other one asks. Why not the gateway default: a run without
  lists gets the entry flow's default tool set under the default approval, which is not what the
  desktop or the iPhone run, and the person would not see the same Assistant on the web. A tool
  without `approval_default` asks (the desktop falls back to a local list the web does not have).
  Consequence, measured on the local gateway: 52 tools allowed, 13 automatic, 39 ask. The web has
  no per-tool settings and no "trust this chat" grant in v1.
- **Start:** `POST /runs/start {flow_id: "@default", interface, session_id, input_data}` (or the
  explicit bundle fields). A web conversation's id is minted like the desktop's (`sess_<hex>`).
  A failed start is never retried automatically (the iPhone's rule).
- **Sessions:** `GET /runs?limit=200&offset=0&root_only=true&include_ledger_len=false&session_kind=chat,discussion`
  (the desktop's pinned query, `client.py:539-561`; the filter is advertised by this gateway in
  `contracts.assistant.runs.list.filters`) folded by `session_id` (`src/lib/session_fold.ts`, a
  port of `core/gateway_sessions.py:159-216`). On live data the two folds are identical (W3 report).
- **History:** `GET /runs/{latest_run_id}/history_bundle?include_session=true&detail=replay`,
  `session.turns[]` → prompt (with attachments) and answer (`history_seed.py:67-100`). A bundle
  with `warnings` shows them.

### 7. Events

- **One turn:** the desktop's stack follower (`run_controller.py:202-432`): one ledger SSE at a
  time, root first; a `subworkflow:<child>` wait pushes the child (the approval lives on the child's
  ledger). Whenever a stream ends, with `event: done` or without it (a proxy idle timeout, a
  gateway restart), the follower asks `GET /runs/{id}`: a terminal run is drained with
  `GET /runs/{id}/ledger` until two reads bring nothing, then popped; a run still going is
  reconnected from its cursor (backoff 1, 2, 4, 5 s). Four connection failures in a row give up:
  the turn is marked lost, its cards are disabled, and the page says to reopen the conversation.
  One stream at a time matters: a real turn nests 3-4 child runs (proven) and HTTP/1.1 gives a
  page six connections per origin. Deltas come from the
  active stream; a (re)connect drops live text and applies snapshots; the durable `llm_call` record
  with the same step id replaces it (`api.md:517-588`). The answer is the ROOT run's flow-end output.
- **Waits:** identity (run, wait key, step id); a `resume` record closes the open waits of its key
  on that run. Tool approval and `ask_user` (`reason: user`, or `evt:…:abstract.ask`) render as
  cards in the conversation. Before answering, the client re-reads `GET /runs/{id}` and answers only
  if the run still waits on the SAME question: same `waiting.wait_key` (`abstractgateway service.py` `run_summary`; the
  iPhone's rule) AND the same batch of tool calls (call id, name, arguments) or the same prompt
  (`waitStillMatches`, `src/lib/run_events.ts`). The key alone is not enough: the runtime reuses
  one key per node for every approval batch (`adapter.py:42-58`), and the run summary carries no
  step id, so a stale card could approve a newer batch nobody saw. An approval whose waiting record
  names no calls is refused. Gateway ask G4 (1057): the waiting `step_id` in the run summary,
  which would make the comparison exact. Then
  `POST /commands {type: "resume", run_id: <the waiting run>, payload: {wait_key, payload}}` with
  `{approved}` / `{approved: false, reason}` / `{response}` (`client.py:209-245`).
- **The person's stream:** `GET /me/events?limit=1` for the head, then `/me/events/stream` from
  it: `run.started` / `run.finished` of a listed conversation, or a person's new run, refresh the
  list (automation occurrences do not); `attention.seen` of a wait closes its card here.
- **Titles:** each row's opening prompt (`input_data` of its first run), at most 40 per refresh,
  four at a time, cached for the page's life; a failed title is retried at the next refresh and
  the list says how many are missing.
- **History:** a turn whose `status` is `failed` or `cancelled` shows as a notice ("This turn
  failed: …", "Stopped."), never as an answer to read aloud.

### 8. Voice in the browser, on the gateway's engines

- **Read aloud:** `POST /runs/{answer run}/voice/tts/stream` (JSON Lines: `queued`, `audio` with
  `audio_b64` WAV, then `done` / `cancelled` / `error`), each WAV decoded and scheduled back to
  back with Web Audio.
- **Dictation (browser host):** MediaRecorder (`audio/webm;codecs=opus`, else `audio/mp4`, else ogg) →
  `POST /attachments/upload` → `POST /runs/{owner run}/audio/transcribe {audio_artifact}` (the
  iPhone's path, `GatewayClient.swift:704-728`; the gateway lists webm, mp4 and ogg among accepted
  types). The text lands in the composer for review (the iPhone's default, backlog 1048).
- **Secure pages only:** browsers expose the microphone to `https://` and `http://localhost` /
  `127.0.0.1` only. Over plain `http://<LAN address>` dictation is unavailable and says so; read
  aloud still works. Remote use needs the gateway behind TLS (`security.md:500-552`).
- **The orb** (W4's design) is v1.1: it is the visual state of the same two flows.

### 9. Scope

- **v1, the Assistant space:** conversation list from the gateway, open a conversation (its
  history), send with attachments, live streamed answer and activity line, stop, tool approval and
  questions in the conversation, read aloud, dictation, sign-in / sign-out.
- **v1.1:** the orb and hands-free voice turn; generated media in answers (image/audio artifacts
  through `runs/{id}/artifacts/{id}/content`); attachment previews; "load more" conversations;
  rename/archive (`POST /sessions/{id}/archive`).
- **v2:** Inbox (the open waits across conversations and automations: the `attention.raised` minus
  `attention.seen` fold the desktop, iPhone and abstractcode already do —
  `gateway/me_events.py`, `abstractcode/web/src/workspace/me_events.ts`); Automations (ui-kit
  `AutomationPanel`); web push notifications (service worker; a gateway ask, see 1057).

### 10. Non-goals

Choosing providers or models per run, editing workflows, workspace folders and tool policy editors
(the gateway console owns them), local models, offline use, any copy of a conversation in the
browser, and the coding surfaces of abstractcode.

### 11. Relation to abstractcode/web

Separate products on the same platform. Shared: the app-server kit, the sign-in machine, the
relative-URL rule, Markdown, the gateway contracts and their folds (the session fold rules are
common to abstractcode's TUI and web, the desktop, and this app). Not shared: the screens, the
workflow model (abstractcode picks among agent workflows; the Assistant runs one), the look. Code
both apps copy (the server guards, the URL check) goes to abstractuic (U1), not across repositories.

## Consequences

- One more npm package to release (assistant seat) and one more catalog row in the gateway (G1).
- The web Assistant moves with the desktop's contract: a change to `run_input.py` or the session
  fold fails the web tests until the port follows (both fixtures are read from this repository).
- The desktop's "stop publishing the managed workflow from the client" (overview item 0) becomes
  more urgent: the web client depends on the gateway reporting the default, not on a desktop having
  run once.
- A non-browser host (ADR 0008) reuses the components and `src/lib/`, `src/gateway/` if it
  implements `src/host/types.ts`; it brings its own layout and, outside the browser, the
  AudioWorklet dictation path above.

## Alternatives considered

- **Inside the Python package, served by a Python server.** Rejected: the gateway runs browser apps
  as Node servers from npm; a Python-served page would need its own sign-in and proxy.
- **Static files served by the gateway.** Rejected by the gateway's design: the app's server holds
  the sign-in and the CSRF pair (`apps.md:425-443`).
- **A mode of abstractcode/web.** Rejected: different audience, different workflow model; it would
  keep the coding UI's weight on the simplest surface.
- **EventSource for SSE.** Rejected: no request headers, so no bearer host.

## Validation

In CI (`.github/workflows/ci.yml`, job `web`): `npm ci`, `npm test` (vitest: fold parity on the
Python fixture, run-input and tool-list parity on cases generated by the desktop's code, the turn
reducer on the desktop's production subrun fixture, the follower against a fake gateway including
a stream closed without `done`, the wait guard, titles, host selection and capabilities, voice
lines, SSE framing), `npm run build` (tsc + vite + relative-URL check) and `npm run test:layout`
(headless Chromium, four widths). The Python job regenerates both parity fixtures and fails on a
diff. The read-only live proofs are in `untracked/apple-web-wave/w3-web-architecture.md`; sending,
approving, answering and voice have not been run against a gateway (backlog 1057 phase 1).
